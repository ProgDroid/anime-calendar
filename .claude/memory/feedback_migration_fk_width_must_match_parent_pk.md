When writing a new `CREATE TABLE` migration for this codebase, the FK column types MUST match the referenced PK column types exactly. Confirm by grepping `migrations/20260401000000_create_tables.sql` (or the latest baseline) for the parent table — `users.id` and `calendars.id` are both `SERIAL` (= `int4` = `i32`). All FKs into them must be `INTEGER`, never `BIGINT`. The only `BIGSERIAL` PKs that warrant `BIGINT` FKs are tables that explicitly opted in (`calendar_invitations.id`, `subscription_events.id`, etc.) — and there are very few.

**Why:** PostgreSQL itself happily accepts a `BIGINT REFERENCES integer_pk` with implicit coercion at runtime — the migration applies cleanly and queries work. But `sqlx::query!` reads the actual `pg_attribute` width metadata at compile time, so it generates `i64` for any BIGINT column. The Rust entity (constructed manually from the row in our convention, see `mappers/calendar.rs`) then fails to compile because the field is declared `i32`. The error only appears when running `cargo sqlx prepare --workspace -- --all-targets` or the first downstream `cargo check`, by which time the migration has been committed and applied to dev. Fixing it then requires a forward-only ALTER COLUMN migration (drop FK → ALTER TYPE INTEGER USING ::int → recreate FK) — extra commit, extra checksum slot, extra noise.

**How to apply:**
1. Before writing any `CREATE TABLE`, grep for the parent PK type: `grep -n "id .*SERIAL\|id .*BIGSERIAL" migrations/20260401000000_create_tables.sql` (and any later migration that introduced the parent).
2. Mirror exactly: `SERIAL` parent → `INTEGER` FK; `BIGSERIAL` parent → `BIGINT` FK.
3. If the entity struct is being authored in the same session, declare its fields using the same Rust type the FK width implies (`i32` for INTEGER, `i64` for BIGINT). The session memo `project_co_editor_phase_0_in_progress` already flagged this as drift point #1 — bake it in upfront, don't discover it later.
4. Concrete example of the bug from Spec 2 / Phase 0: `migrations/20260505000001_create_calendar_editors.sql` declared `calendar_id BIGINT REFERENCES calendars(id)` but `calendars.id` is `SERIAL`. The entity in `entity/calendar_editor.rs` was correctly authored as `i32` once the convention was discovered. Fix shipped in `migrations/20260505000003_fix_editor_invitation_fk_widths.sql` on 2026-05-05 — drop FK, ALTER TYPE INTEGER USING column::int, re-add FK. Cost: one extra migration + commit. Avoidable.
